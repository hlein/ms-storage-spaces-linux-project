# Security review

Scope: the `spaces` command and the `storage-spaces` library as of the
write support (0.2.0), reviewed 2026-09-29; pool management (`spaces pool`,
`space`, `disk`; Stage 3), reviewed 2026-09-30; the ReFS reader (`refs`
and the `refs` library, Track B), reviewed 2026-10-03; the health guard
(1.2.0), reviewed 2026-10-07; everything, by the code audit of 2026-10-16
(1.2.1), whose findings 1.2.2 fixes as the rows below say.

## Threat model

* **Untrusted disks.** Any disk with a Storage Spaces partition can be
  plugged in; the udev rule then runs `spaces attach` as root, which parses
  every piece of metadata on it (GPT, SPACEDB header, pool database,
  records, write-back cache and its checkpoints, parity journal, dirty region
  log). Hostile metadata must not corrupt memory, exhaust memory or CPU,
  make the tool write anywhere, or expose data to other users.
* **Local users.** Attached spaces and the processes serving them must not
  give users without access to the member disks access to their contents.
* **Writes.** Writing happens only when asked for (`--rw`); on a pool whose
  metadata was crafted to mislead, writes must still stay inside the pool
  partitions of its member disks.
* **Management.** `spaces pool|space|disk` change metadata and move data
  only when asked for (`--yes`), only on the disks named, never on disks in
  use, and leave a pool that opens after a crash at any point.
* **Untrusted ReFS volumes.** `refs` is run by hand, and as root by
  `mount.ReFS` when fstab or udisks2 mount a volume (a disk plugged in, a
  desktop's file manager); it writes only when asked (the writing commands
  with `--yes`, `refs mount --rw`, the mount options `rw,refs.rw`): hostile
  metadata must not corrupt memory, exhaust memory or CPU, make it write
  outside the volume, or show the volume to users it was not mounted for.

## Findings and mitigations

| Area | Status |

| ReFS volumes on hostile input | No `unsafe` code in `refs` or `refs-cli`. Every metadata page `refs` reads must match the checksum (CRC-64 or SHA-256) its reference records, the superblock and checkpoint their own, the boot sector its sum; a mismatch is an error. The data of integrity streams must match its CRC32-C or CRC-64 on every read (test `integrity_streams_refuse_damaged_data`). B+-trees deeper than 16 levels and chains of more than 1024 data levels are refused, reads may not leave their container, nor (since 1.3.1) may the runs of a file the writer changes (`refs check` reports one that does), a virtual cluster must have the bit between its container's clusters and its id clear and a container id must fit an address, and a volume larger than its device does not open (tests `a_virtual_cluster_with_the_container_bit_set_is_no_address`, `a_run_past_its_container_is_reported_and_not_written`, `a_container_id_beyond_any_address_is_refused`, `a_volume_larger_than_its_device_is_refused`), page buffers are sized by the page size of the boot sector (4 KiB or 64 KiB clusters only). Fuzz targets `refs_parsers` (boot sector, page references and headers, nodes, rows and records, LZ4 blocks and ZSTD frames of compressed containers: a block must decompress to exactly its unit, every back reference inside what it made; a ZSTD frame's header must declare a window of at most 8 MiB and, if it has one, the unit's size before the `ruzstd` crate (pure Rust, with some `unsafe` in its ring buffer, fuzzed upstream) decodes it; what is copied out is capped at the unit, while what the decoder allocates inside is bounded by the crate itself: `ruzstd` 0.9.0 let a tiny frame exhaust memory (RUSTSEC-2026-0344), so 1.2.2 takes 0.9.1, and `cargo deny` and `cargo audit` run every week in CI to catch the next one; units are checked against their CRC32-C first) and `refs_volume` (fixtures patched by the input and read end to end: partition table, superblock, checkpoint, tables, directories, records, extents, streams, links, compressed containers, then checked as `refs check` does; fuzzing builds accept every checksum so that patched pages reach the parsers); a 2-minute run of each found nothing (2026-10-03), nor did a 4-hour run (1.87 billion runs of `refs_parsers`, 7.65 million of `refs_volume`) or a second 4-hour run of `refs_volume` beside the writer's (614,147 runs, 2026-10-03). `refs_write` patches the small fixture and runs every writing operation on it, asserting that no byte lands outside the volume; it found an overflow in its own harness and then a real fault: a boot sector claiming a volume that ends before a checkpoint slot made a commit write the new checkpoint past the volume's end. It also found `refs check` without an end on rows claiming 2^64 clusters (a reference count row, an allocator bitmap) and on a directory named below itself, overflowing on reference count rows inside others and on free counts past 2^64, and stopping at a page whose node does not parse or a damaged upcase table; since 1.3.1 the check takes rows by what they hold, visits each directory once and reports those as problems, in time proportional to the volume's pages and files (tests in `crates/refs/tests/check_bounds.rs`, all failed on 1.3.0's code). No process runs the full check by itself: `mount.ReFS`, udisks2's mounts and the guard run the quick checks (boot sector, superblocks, checkpoints, log pages), and `spaces check --deep` and `refs check` run it on request. The FUSE mount is read-only and only for the mounting user unless `--allow-other`; named streams over 64 KiB are not handed to the kernel as extended attributes. Since 1.2.2 every FUSE request is served under `catch_unwind`: a panic fails that request with EIO and the mount goes on, and after a panic inside a change (`--rw`) every request fails so (the volume in memory may be half changed); in 1.2.1 each panic ended a serving thread, the mount after four (with `--rw` after the first; test `a_panic_in_one_handler_does_not_end_the_mount`). |
| Writing ReFS | Only `refs set|overwrite|write|create|rename|move|link|clone|delete|mkdir` (with `--yes`) and `refs mount --rw` write, only to a volume whose log has nothing past its checkpoint (Windows would replay it over the changes), and only to a device or image given by path (never a pool's space; the read-only mount's device refuses every write). The read-write mount is for the mounting user (FUSE's default permissions, the mount point's owner) unless `--allow-other`. Since 1.3 the writing commands and `refs mount --rw` hold the device or image with an exclusive lock and a read-only mount with a shared one, and refuse while another process holds it the other way, naming it (test `writers_wait_for_whoever_holds_the_volume`; the code audit of 2026-10-16 found that `refs write` during a mount for writing was lost when the mount wrote its view of the volume over it); the buffers of files open for writing are temporary files without a name (`O_TMPFILE`, else a random name unlinked at once) of mode 0600 (`buffers_of_files_open_for_writing_are_private`; until 1.3 mode 0644 under the usual umask and a name others could guess, so that another user could open one and read what was written). A commit writes changed pages only to clusters free in both the old and the new allocator state (clusters freed by the transaction stay reserved until it commits), flushes, and then writes one checkpoint cluster into the older slot and flushes: the old checkpoint stays intact until then (test `setting_times_and_attributes_commits_copy_on_write` checks the write order and that nothing the old checkpoint reaches is written; test `interrupted_writes_leave_the_old_or_the_new_volume` replays every prefix of the writes of a create, mkdir, delete, link, stream write, rename and move over a file, clone to a new name and replacement of a stream in clusters, also with the last write torn in half, and finds the old volume each time (names and what the files hold), the new one only once its checkpoint is down, with valid pages and allocators). Since 1.3 the pages the commit before replaced stay reserved too, so the older checkpoint stays intact through the next commit as well, as Windows keeps it (test `the_older_checkpoint_stays_whole_through_the_next_commit`; the code audit of 2026-10-16 found that the next commit took them, overwriting the older checkpoint before its own was down), and a commit that fails is followed by reading the volume again from the disk, its checkpoint down or not, and if that fails every later change is refused (`a_failed_commit_leaves_the_volume_as_on_disk`; until 1.3 the volume went on with the checkpoint before, so that the next commit could write over the pages of the one on disk and then replace it). Windows writing into a volume `refs` wrote crashed Windows (bugcheck 0x149, three times, each time it wrote into a hole of one file, in the item 2.7 round trip of 1.3): `refs` packed the extent map in a file's record tight, without the room for a further record Windows keeps there and relies on; since 1.3 maps have that room (test `maps_have_the_room_windows_leaves`; Windows then wrote into every file the round trip made, healthy). A cluster the block reference count table counts other references for (clones, deduplication) is never freed nor overwritten in place: deleting a file lowers its count instead. The code audit of 2026-10-16 found that replacing a file's data reset its record's counter of stream set ids, so that the next named stream in clusters took the set of an existing one and both read its data (deleting one then broke the file); since 1.2.2 the counter is kept, a new set takes an id past all of the record's (test `rewriting_a_file_keeps_its_stream_sets_apart`), `refs check` reports keys twice and streams whose set has no rows (`check_finds_rows_twice_and_streams_without_their_set`), and `refs_write` writes and deletes named streams. The audit also found three ways `refs mount --rw` lost data: a rename over a file to a name the library refuses deleted the file first, closing a reader of a file open for writing dropped the writer's buffer (its next write: EBADF), and a failed write-back was forgotten; since 1.2.2 the rename was checked whole before the delete, only handles open for writing hold the buffer, and a failed write-back stays and is reported by every flush (tests `a_refused_rename_over_a_file_leaves_it`, `closing_a_reader_leaves_the_writers_buffer`, `a_failed_write_back_is_kept_and_reported_until_written`). Until 1.3.0 a rename over a file, a clone to a new name and replacing a stream in clusters took two commits each (a crash between them left the target deleted or empty, audit findings W2 and M15); since then each is one (`Volume::rename_replacing`, `Volume::in_one_commit`: the steps write their pages, one checkpoint names them all), as the replay test above shows. Creating a file and writing its data through the mount stay two (empty after a crash between them, as on other file systems). Every page a commit writes is checked in the tests the way Windows checks pages (rows parse by their sizes, the key index names live rows, the free bytes add up); Windows refused a page with a zeroed hole before that rule was known. Since 1.3 a directory's names are ordered as the volume's upcase table says, where Windows looks them up (1.2.2 took Unicode's upper case: test `new_names_go_where_the_upcase_table_puts_them`), and `refs check` reports names out of that order, so that `refs_write` fuzzing would see such a change; names Windows programs could not open (a last dot or space, device names) are refused. |

| Memory exhaustion | The sizes read from disk that decide an allocation are bounded before allocating: database ≤ 64 MiB and ≤ 1024 formatted pages, cache and journal slot areas ≤ 64 MiB, checkpoints ≤ 16 MiB (found in this review: a crafted checkpoint could claim the 125 MiB of a journal area per copy; now capped), checkpoint area offsets ≤ 2^56 for the cache and the parity journal (found by fuzzing: a journal area offset near 2^64 overflowed), slab and extent numbers ≤ 2^32, and an extent maps one slab at least (not checked in 1.2.2: an extent of no slabs left its space healthy, reading zeros where it belonged; found after the release by the boundary values tried on every fixture). Since 1.2.2 also the numbers of a space's placement policy and extents (columns ≤ 1024, copies ≤ 16, local groups ≤ 64, redundancy ≤ 3, sizes and ranges ≤ 2^60, slot areas ≤ 2^56; see "Plausible values" in `docs/storage-spaces-format.md`): in 1.2.1 a copy count of 2^31 made the checks loop for minutes, 2^64 − 1 overflowed, and a space of 2^62 bytes made `segments()` (the device-mapper table) loop over every row; now a space beyond a limit is refused for itself, its pool's other spaces unaffected (test `numbers_beyond_any_pool_are_refused_not_computed_with`: each of 0, 1, 2^31, 2^32, 2^36, 2^56, 2^63 and 2^64 − 1 in every field on every fixture, and in the slot, checkpoint and data offsets of cache and journal headers with their CRC sealed again, each case within 5 s), and segments follow the extent runs. Also since 1.2.2: what a decoded structure takes is bounded too, not only what is read for it. The index of a write-back cache keeps runs as their words on disk and may take 256 MiB at most (a slot area of 64 MiB in one-sector runs took 700 MiB, now 244 MiB: test `a_cache_index_of_many_runs_stays_small_and_quick`); of the copies of the pool database only the one used is kept, the others as a digest keyed at random (five differing 64 MiB copies took 370 MiB, now 124: `differing_copies_of_a_large_database_are_not_all_kept`). Work that grows with what metadata claims is bounded as well: the journal check counts the ranges a parity journal lists (a run of 2^30 stripes was walked one by one), the health of a pool is worked out once for all its spaces (10 000 spaces with 40 000 hidden ones: 8.5 s), out-of-date extents are looked up in log time, the ReFS log check looks back for a multi-page record instead of reading the log whole and reads a log whole only up to 2 GiB, and `spaces attach` makes devices for 128 partitions of a space at most and waits for udev 60 s at most in a run (test file `crates/storage-spaces/tests/work.rs`). Since 1.3.1 the writers of a cache and a parity journal are bounded alike (audit 2026-10-21, SPB-03): the cache writer keeps a chunk's valid sectors as runs (a checkpoint of 4 KiB naming 256 whole chunks of 64 MiB took 32 MiB to continue: test `a_cache_of_whole_chunks_of_64_mib_is_continued_in_little_memory`), the journal writer a run's consistent stripes as runs read in one pass (an entry of 10 000 runs, 20 KB, took 327 MB and did not finish: `a_journal_entry_of_ten_thousand_runs_is_continued_in_one_pass`), a journal's decoded entries take the cache index's 256 MiB budget (`a_journals_entries_have_the_cache_index_budget`), and an entry that does not fit its slot is an error instead of being cut off (`a_run_too_long_for_a_slot_is_an_error_not_a_cut_entry`). Not bounded: what a check that hangs has allocated (its thread is left to the end of the process), and `refs check` keeps one entry per cluster of the compacted containers files reference (containers of at most 2^20 clusters). |
| Command execution | External programs (`dmsetup`, `systemd-run`, `nbd-client`, `losetup`, `udevadm`, `journalctl`) get separate arguments, never a shell; one `sh -c` checks fixed program names, and since 1.3 the child that checks a pool is started by `/bin/sh -c 'ulimit -v N; exec "$0" "$@"'`, the program and its arguments passed as the shell's positional arguments, never in its script (`check::spawn_child`). Device-mapper names are made of `[A-Za-z0-9_.+]` only, whatever the pool and space are called. Since 1.3 every device-mapper device attach makes carries the UUID `STORAGESPACES-<pool guid>-<space guid>[-p<n>]`, and only devices with a space's UUID are removed for it: in 1.2.2 the failed attach of a space whose device name another space's device had (`Фото` and `Игры` both give `____`) removed that other device. |
| Where writes go | Every slab write resolves through `Pool::slab_location`, which refuses slabs beyond the member's pool partition; database copies go to the fixed offset in that partition and must fit it (until 1.3 a partition table that made the pool partition shorter than its database got the copy written past the partition's end: test `database_copies_stay_inside_their_partitions`). A misleading pool can at worst overwrite its own partitions, which `--rw` asked for. Checked by the fuzz target `pool_write` and the test `writes_on_corrupted_metadata_stay_in_the_pool_partitions`: whatever the metadata, no write lands outside a member's pool partition. Found by `pool_write`: a user space whose record claims a part of an address space, as only tiers do, made writes start below its layout (a panic); such spaces are now refused for writing. Found by the code audit of 2026-10-16 (fixed in 1.3, each with a test that failed on 1.2.2): the writer trusted the shapes of hidden structures (a cache whose chunks are not the space's stripes made destaging assert, a dirty region log smaller than its two headers wrapped the second header's offset, records that do not assemble made the allocator place a new row on slab 0 of each disk, over the metadata space, and its update made every copy of the database unreadable); such spaces are refused for writing, and the allocation fails (tests `hidden_structures_of_other_shapes_are_refused_for_writing`, `rows_are_not_placed_over_the_metadata_space`). After a write or flush a disk fails, the writer writes nothing more until the space is opened again (test `nothing_is_written_after_a_failed_write_or_flush`). |
| What is written | `--rw` is refused unless the pool is clean and every structure the writes touch is understood (see the user guide); the udev rule and the attach units (`storage-spaces-attach.service` at boot, `storage-spaces-attach@.service` for each member that appears) never pass `--rw`. Since 1.3.1 a parity space whose journal header counts extent runs or stripes of another size than the space's is refused for writing (1.3.0 wrote entries the journal then refused to load, and the space did not open again; audit 2026-10-21, SPW-02, test `a_journal_counting_runs_of_another_size_is_not_written`), and journal checkpoint areas too small for a checkpoint count as none (1.3.0 wrote a checkpoint over the journal's header into areas of no bytes at 0). |
| Exposure to other users | Block devices (`/dev/mapper/ss-*`, `/dev/ublkb*`, `/dev/nbd*`, loop devices) are created by the kernel as root:disk 0660. NBD sockets are owner-only (0600) from the moment they can be connected to: bound in a directory of their own (0700) beside their path, made 0600, then moved into place (1.2.2 made them 0600 right after `bind`, which listens at once, so that a connection could come before; earlier they followed the caller's umask); the attach path keeps them in `/run/storage-spaces` (root, 0755). The FUSE backend of `spaces` (a space as a file) is read-only and without `allow_other`, so only root can open it. `spaces export` writes a new image only its owner may read (0600; 1.2.2 used the umask, 0644 for most), complete or not at all (test `exports_are_private_and_whole_or_absent`). `refs mount` run by root (through `mount.ReFS`: fstab, udisks2) mounts with `allow_other` and default permissions, as udisks2 mounts NTFS: every user may read the volume's files, and with `rw,refs.rw` write them as the mount point's owner; run by a user, the mount is that user's unless `--allow-other`. State files are root's. Names read from disks (pools, spaces, disks, ReFS files and streams) are shown to people with control and format characters escaped (`report::printable`: reports, refusals, plans, `spaces pool health`, `refs ls|stat|map|check`); until 1.2.2 they reached terminals, the world-readable report files and the journal as they were, so that a disk's names could send escape sequences or forge report lines (tests `names_from_disks_cannot_steer_a_terminal`, `names_reach_terminals_escaped`). |
| Which disks management writes | Every command prints its plan and writes only with `--yes`. `pool create` and `disk add` refuse disks that are not blank (a partition table, file system or pool data in the first or last MiB) unless `--wipe`, which clears their first 17 MiB and last MiB first (`disk add --wipe` cleared nothing until 1.3). A plan is carried out on the devices opened to make it (until 1.3 the paths were opened again, which by then could name other disks), and whether a device is a block device follows from what it is (until 1.3 from whether its path began with `/dev`). Members are opened exclusively: block devices with O_EXCL, which fails while they are mounted, assembled or held by device-mapper, and every member (block device or image file) with an exclusive lock, which fails while a server or `export` holds its shared lock on it or another writer its exclusive one; the refusal names the holder (from `/proc/locks` or the device's holders in `/sys`). The packaged `spaces` writes members through plans and `--yes` only: until 1.3 it carried the write tests' hidden `write-pattern` (now the separate `spaces-pattern`, which the packages do not install) and stopped plans after the step `SPACES_STOP_AFTER_STEP` named (now in builds with the feature `test-hooks` only; tests `the_root_binary_writes_no_pattern`, `the_root_binary_ignores_the_step_hook`). Read-only servers share the members with the servers of the pool's other spaces (test `the_spaces_of_a_pool_are_served_at_once_and_writers_wait`; `tools/multi-vm-check.sh` on the VMs); until 1.3 they held them exclusively too, so that a pool's second server-backed space could not be attached (audit O1). (Found in the review of 2026-09-30: only paths spelled under `/dev` got O_EXCL, so a block device named through a symlink did not, and image files had no exclusion at all: a management command could change a pool whose images `serve-ublk --rw` was writing.) |
| Management on hostile metadata | Planning starts with `check_pool`: the pool must be clean (no missing disk, stale copy or torn record; repair and removing a missing disk accept missing disks and nothing else) and every record decode into a model that encodes back to the same bytes, so nothing unknown is rewritten. The fuzz target `manage` runs every planner on patched pools and checks every action of the plan: writes only inside the members' pool partitions (removing a pool: only its partition tables), or to the disk being added. Sizes are rounded to whole rows with checked arithmetic and bounded to 2^32 slabs (found in this review: a size near 2^64 wrapped to a space of 0 bytes, and a record's allocation unit of 0 would have divided by zero when growing its space); the fuzz target `create` now draws sizes from the whole 64-bit range. Found by the 24 h run of `manage`: records claiming more slabs of a disk than its size made the count of its free slabs overflow, and in a release build new extents could have been placed over data; extents beyond their disk or overlapping each other now stop the planners (every pool of the corpus and the scenarios passes the check). Found by the second 24 h run of `manage`: removing a pool or a disk rewrites the partition table where the table's own headers say, unchecked; a header claiming a sector near 2^64 overflowed, and a crafted table could have directed those writes into the disk's data. The headers must now sit at the disk's first and last sector and the entry arrays outside the partitions' area, with checked arithmetic (test `crafted_partition_tables_are_not_rewritten`). Found by the code audit of 2026-10-16: renaming to a name of 65 535 characters wrapped its length and wrote a record no reader decodes into every copy of the database; since 1.2.2 names are 1 to 256 characters, a string too long for its count is an error, and every record a plan writes must decode before it is written (tests `a_name_too_long_for_its_record_is_refused`, `records_that_do_not_decode_are_not_written`). Found by the same audit, fixed in 1.3 with tests that failed on 1.2.2: `pool scrub --repair` of a parity space whose units are larger than the MiB it reads at a time recomputed a whole unit from the damaged MiB on, past the end of the slab into the next one; `space resize` of a space of local groups placed its new rows where no row starts; a database copy was written header first, so that a write torn by a crash made it the newest; disks too small for a pool and columns that overflow with their copies were computed with wrapping arithmetic. Updates are made on the database as readers read it (until 1.3 the model stopped at the last page formatted whole, and a database whose page in use was formatted in part, as in 17 of the fixtures, lost that page's records). Since 1.3.1 `check_pool` also bounds the numbers plans compute where they write from (audit 2026-10-21, SPW-01, SPW-02): space numbers to the 64 database places of the metadata space (2^42 overflowed adding a disk, a panic; 70 put a database past the slab) and each disk's data area to its partition (a disk claiming more got new slabs past its partition); resize refuses allocation units that are not whole slabs and extents that are not whole groups, and follows the groups the extents map; tier templates of an unknown resiliency, one tier and tiers beyond a space's size are refused instead of a panic or a plan; the writer stops after any failure once it has written (tests in `crates/storage-spaces/tests/management_metadata.rs`). |
| Crashes during management | A plan's steps are made durable one after the other; pool database copies are written one per step; data is copied into free slabs before the one database update that records the move. Tests replay a crash after every step of creating a space, retiring a disk and repairing (`ops.rs`), and Windows 11 took pools cut after steps of creating a space, adding and retiring a disk (`mgmt-crash.json`). |
| Denial of service by panics and hangs | Since 1.3 `spaces attach` and `spaces check` check each pool in a child process of its own (`spaces check --json --here`), all at once, with an address space limit (2048 MiB, `SPACES_POOL_MEMORY`; set by `ulimit -v` in `/bin/sh`, which then runs the child) and a deadline (120 s, `SPACES_POOL_TIMEOUT`, within `SPACES_ATTACH_TIMEOUT`; none for `spaces check --deep` unless the variable sets one, test `a_pools_checks_take_120_s_and_the_deep_ones_their_time`) after which it is killed: a pool whose checks allocate without bound or hang gets a failed `space.checks` report naming the limit, nothing of it is attached, and the other pools are attached as usual; the parent reads the child's reports back from their JSON and opens a pool itself only to attach the spaces its child reported on (tests `a_pool_whose_checks_allocate_without_bound_fails_alone`, `a_pool_whose_checks_hang_fails_alone_in_time` with the test hooks of the feature `test-hooks`, `tools/attach-crash-check.sh` case `children`; until 1.3 every pool was checked in the one process of the run, and such a pool took the run with it: 9b8b369 with the same hooks aborted, "memory allocation of 67108864 bytes failed", or hung until killed, with no report at all). Within the child, opening each pool and the checks of each space run on a thread of their own (`storage_spaces::isolate`): a panic there (a defect a hostile disk reaches; release builds check integer overflow) fails that space with `space.checks`, checks that take longer than 40 s (`SPACES_CHECK_TIMEOUT`) make it suspect, and the other pools are attached all the same; a panic while attaching a space that passed fails that space only. `spaces check` and `spaces info` run the checks the same way (`--deep` without a time limit); the servers, `export`, `refs mount` and the other `refs` commands catch a panic in the checks and refuse, and since 1.2.2 `refs mount` answers a request that panics with EIO and goes on; the scan of the block devices skips a device whose partition table makes the parser panic. A thread that hangs is not killed but left to end with the process, and what it allocates is bounded only as the parsers bound it. Since 1.3 the external programs attach and detach run (dmsetup, losetup, nbd-client, systemctl, udevadm, journalctl) are stopped after 120 s or what is left of the run's time (test `programs_are_stopped_in_time`), and a run waits for another one's lock only that long, naming the process that holds it (`the_lock_is_waited_for_in_time`); until then a program hung on a device held the run for ever, and with its lock every later attach and detach. Until 1.2.1 a panic in the checks of one pool ended `spaces attach` for every pool after it. Tests make the checks panic or hang (`checks_that_panic_or_hang_stop_their_space_only`), make the devices panic under the gate of the servers and `export` and under the checks of a ReFS volume (`checks_that_panic_refuse_the_space_to_the_servers_and_export`, `checks_that_panic_fail_the_volume`), make a FUSE request panic (`a_panic_in_one_handler_does_not_end_the_mount`), and read the limit (`the_checks_take_40_s_unless_the_variable_says_otherwise`); `tools/guard-check.sh` attaches a healthy pool beside a hostile one on the test VMs. The fuzz targets check that the parsers do not panic. |
| Release integrity | `SHA256SUMS` lists the checksums of the release files and is not signed (there is no signing key): it shows a damaged download, not a file swapped on the release page. Since 1.3 the static binaries are built by `tools/build-static.sh`: the paths of the build machine (source tree, crates, target directory, and the toolchain's sources, which the standard library's code compiled into them names) remapped, symbols stripped; two builds of one tree in different directories give identical binaries that name no path of the build machine (`tools/repro-check.sh`, 2026-10-18: `spaces`, `spaces-pattern` and `refs` alike; since 2026-10-22 it also fails on a binary naming the home directory, the toolchain's sysroot or the build directories: the first build of 1.3.0 still named the toolchain's sources under the home directory, 45 strings in `spaces`, and 1.2.2's binaries named the crates and the toolchain's sources there, 133 strings). The licences of what they link (the Rust crates, the Rust standard library, musl) ship with them: `THIRD-PARTY-NOTICES.txt` beside the binaries, in the deb under `/usr/share/doc/storage-spaces` (with a DEP-5 `copyright` naming the copyright holder), in the Arch package under `/usr/share/licenses` (`tools/third-party-notices.py`; until 1.3 none shipped, and the deb's `copyright` was the bare GPL text). CI runs with read-only permissions, its actions pinned by commit and its tools by version. |
| Health guard (1.2.0) | Nothing that is not healthy is attached or mounted without being asked: the udev rule, the attach unit, `mount.ReFS` and udisks2 pass no flag, so a degraded, suspect or failed space is refused, and a ReFS volume that is not healthy is not mounted; `--degraded` and `--force` read such spaces read-only only, a failed one is never read, and every writing path needs a healthy verdict. udev hides the devices of a space attached past its verdict from udisks2. The checks parse more of a hostile disk as root at attach time: the partition table of each space (the entry array bounded to 4096 entries of at most 4096 bytes), boot sectors, the ReFS superblock and its copies, the checkpoints, since 1.3 the container table (the volume opened as `refs` opens it, to find where the log is: 3.1's and logs away from the starts seen were not found, and 3.1's was skipped) and the log's page headers (read a MiB at a time over at most 2^22 pages; at the first cluster of at most 64 containers), and the stripes the parity journal lists (at most 1 GiB). Every address they compute from those numbers is checked: in 1.2.1 a partition entry, a GPT header, an NTFS boot sector or a ReFS boot sector or superblock whose numbers lie beyond any disk made them overflow (a panic, found by the code audit of 2026-10-16, not by fuzzing: the fixtures hold no file systems); such tables and volumes are suspect now, a ReFS volume must fit its partition (tests `partition_entries_of_any_numbers_are_reported`, `partition_tables_beyond_any_space_are_suspect`, `boot_sectors_claiming_any_size_are_suspect`, `checkpoints_beyond_the_volume_fail_it`). The fuzz target `pool_open` runs the guard over every patched pool, `refs_volume` the ReFS quick checks; fuzzing the guard found an endless walk over a space's hidden spaces whose parent links formed a cycle (now each is visited once). The headers of a space's write-back cache, parity journal and dirty region log are read from every copy of their mirror since 1.2.2 (in 1.2.1 from the first only, and a damaged one was taken for no structure: one zeroed sector made a cache and the newer data it held vanish, the space healthy; test `zeroed_headers_of_hidden_structures_never_make_them_vanish` zeroes each of the 216 header copies of the corpus: 207 degraded and reading as before, 4 failed, where a cache kept once held slots, and 5 notes of a structure never written, where the header was zero everywhere with nothing behind it; none skipped, none writable). Format invariants make opening a space refuse metadata that could make it read the wrong data without a second copy to notice it (a slab mapped twice, extents or log entries outside the space, since 1.3 a fixed space with a row left without an extent, which 1.2.2 called healthy and read as zeros; see `docs/storage-spaces-format.md`). Since 1.3 the partitions of a space are read once, by the checks, and attach makes devices for those: a lost primary GPT header is read from its backup (suspect; 1.2.2 called a space whose first 4 KiB were overwritten healthy, "no partition table", 85 mutants of the 1.2.2 oracle campaign, test `a_space_whose_partition_table_lost_its_start_is_suspect`), a protective MBR without a GPT is suspect (1.2.2 took it for an MBR partition), and an NTFS volume smaller than its partition has its boot sector copy looked for after the volume, where Windows writes it. The copies of the extent runs a mirror's dirty region log lists are compared within the read budget: where they differ, outside what the write-back cache holds, reads fail and the space is suspect (1.2.2 called the crashed mirrors of the corpus healthy; test `crashed_mirrors_are_suspect`). Reports are written as root into `/run/storage-spaces/reports` (0644: names and GUIDs of pools, spaces and disks, no data), the directories made 0755 whatever the umask (1.2.2's `refs` made them under its unit's `UMask=0077`, 0700, so that only root could read its reports). Since 1.3.1 a row of a thin space that has extents for some of its columns only is failed (Windows allocates a row's columns together) and a mirror row with fewer current copies than its policy keeps degraded, and the writer refuses both: 1.3.0 called them healthy, and writing into such a thin row allocated it again, the pool database then holding two extents for one column on every disk and the pool no longer opening (audit 2026-10-21, SPA-01; tests `a_thin_row_missing_a_column_is_failed_and_not_written`, `a_mirror_row_short_of_a_copy_is_degraded`). Since 1.3.1 the areas the header of a write-back cache or parity journal names (slots, checkpoints, chunks) must lie inside its space, on rows it maps and apart from one another, and the tiers of a fixed tiered space must follow one another to its end, none without extents; otherwise the space fails, where 1.3.0 called it healthy and read zeros (audit 2026-10-21, SPB-02; tests `a_cache_header_naming_regions_its_space_does_not_hold_fails`, `a_journal_header_naming_regions_its_space_does_not_hold_fails`, `a_tiered_space_whose_tiers_do_not_hold_it_fails`). Since 1.3.1 the listed runs of a tiered space's mirror tier are compared too (1.3.0 called such a space healthy where its copies differed), runs with one copy at hand are not called compared, unallocated ones do not use the read budget, copies of a header page of the log that list different runs in the same generation make the space suspect, and a log too small for its two header pages fails it (audit 2026-10-21, SPG-01 and SPB-05; tests in `crates/storage-spaces/tests/dirty_regions.rs`). A header copy of a write-back cache or parity journal that does not check out by itself (another space's, a geometry no journal has, areas outside the space) gives way to the other copy, as a damaged one does, instead of failing the space (test `a_header_copy_that_does_not_check_out_gives_way_to_the_other`). The device-mapper mapping refuses rows whose only copy is out of date, and compares the copies of the runs a mirror's dirty region log lists first, refusing where they differ or exceed 1 GiB (audit 2026-10-21, SPB-06; tests `a_row_with_only_an_out_of_date_copy_has_no_segments`, `a_mirror_whose_listed_run_differs_has_no_segments`). Since 1.3.1 a primary GPT whose header or entries do not check out gives way to a sound backup, for the guard as for finding a member's pool partition, MBR partitions are numbered by slot, an NTFS volume of no sectors is suspect, and two spaces of one GUID or a name holding a NUL are pool issues (tests in `crates/storage-spaces/tests/odd_metadata.rs`). |

## Remaining risks

* A hostile pool attached read-only can make reads fail or return its own
  (hostile) data; that is inherent in reading it.
* Writing trusts the pool it was asked to write: with `--rw` on a crafted
  pool, the data of its spaces can end up anywhere inside its partitions.
* Image files are locked with advisory locks: other programs (a hypervisor
  using the same images, `dd`) are not kept out.
* Windows 11 24H2 bugchecked when a pool of four disks arrived with one
  disk absent, whoever had created the pool (`docs/plan.md`, Stage 3
  progress). Handing Windows a pool with a disk missing is a risk to the
  Windows machine, not to the pool.
